- Price sheets share deterministic calculation and explicit user overrides across screen/chat/live reports; Senior pallets join article-only on selling-unit 28 (not corresponding UM), reject conflicts, and disclose denominator gaps. NIR pallet lines supply the monthly inbound count; configured MP capacities stay labeled, client network fees % come only from the rules' client fee table (store/central name match, 0% when unlisted, each store its own fee in central lists), never from invoice history; distribution is per Senior cursă (carrier FF lines "TRANSPORT DIST <cursă>" ÷ pallets invoiced to stores mapped to it by store city/county rules, a labeled proposal the user can override per store or county — admin choices are merged server-side into the rules (`price_route_remember`: `storeRoutes` beat city/county, county choices go to `countyRoutes`) so they are never asked again, browser-only overrides remain only for sales users; invoice lines without a pallet coefficient are reported, never converted to estimated pallets). Transport uses latest prices: recent-window cost per truck/cursă ÷ longer-window load (pallets per truck/trip), never annual or closed-month averages; central-partner lists weight store cursă tariffs by delivered pallets, but a product sheet on the client average weights only the stores that bought that product, by its pieces sold (`productAverageRoute`), so it matches the per-store table. A cursă alone on its route keeps its own lei/palet (latest lei/cursă ÷ load pallets/cursă); curse of the same route (rules `routeGroups`, defaults from the user's table, a cursă on at most one route) leave on the same truck, are shown as one row/option per truck (`truckRows`), and share one tariff: Σ latest cost ÷ Σ latest trips ÷ (Σ load pallets ÷ Σ load trips); the sheet receives the route's cost/trips/pallets (`routeDistribution`) because it re-derives lei/palet from cost ÷ pallets. Supply shows per-pallet and per-kg tariffs with an explicit basis; labour is the rules' people × hour cost ÷ speed (+ overhead %), recomputed in configuredSheet, never stored as server default rates. Why: prefilled inputs without silently presenting estimates as verified commercial prices.
- Supply transport load (pallets per truck) comes entirely from Coral raw-material supplier orders: pallets = ordered kg ÷ range kg/palet (configuredRawPalletKg), trucks = each delivery day's pallets (all suppliers) ÷ the configured truck capacity (`truckPallets` in the price rules, default `TRUCK_PALLETS`) rounded up; never NIR PALET lines or invoice truck counts, products without a norm are listed, not counted. Why: NIR pallet lines mixed empty-pallet purchases and missed suppliers that do not invoice pallets.
- Price calculator rules (labour lines, pallet norms, traded goods, truck capacity, routes (curse on the same truck) and city/county maps, client network fees, default margin/EUR buffer/extra loss, cost/load windows) live in Cloud `argus_price_rules` (append-only, latest row active) via `_shared/priceRules.ts`; `price_options`/`price_list` load them every run and return them so the screen sets the same active rules; code constants are only the initial defaults and built-in lines cannot be deleted. Why: the user edits rules without code changes, and server and screen must compute identically.

- Price sheets: margin % and profit % are shares of the selling price without fees: price = (production cost + distribution) ÷ (1 − margin% − profit%); minimum price (break-even) = cost + margin; network fees added last: proposed = price ÷ (1 − fee%); real profitability = (price − fees − minimum) ÷ (price − fees). Why: the user prices margin and profit from sales, not as markup on cost.
- Senior `sql` live reads return at most 500 rows: any read that can exceed it must use `seniorSqlAll` (stable ORDER BY + OFFSET pages). Why: the bridge truncates silently.
- Partner mirror (`_shared/partnerMirror.ts`, maths in `partnerMirrorMath.ts`, screen Calculator preț → Oglindă parteneri) takes real qty/value per central partner × product from Senior invoices in the chosen period and costs them with price-list sheets of a chosen cost month (default the last whole month, `lastClosedMonth`, also the price calculator's and cost structure's default) (`price_list` per partner); incomplete sheets are listed, never counted. Partners are picked by hand, grouped by the Senior partner classifications "Subgrupa" → "subgrupa 2" (`D_Parteneri_Clasificari`, joined as one derived table, never per-row subqueries). The future projection keeps each product's average monthly quantity of the period, at the current selling price (`currentPrice`: default the partner's latest invoice day for the product, positive lines only; or the last-month / period average; missing bases fall back latest → last month → period) and today's costs (`projectLine`); the simulator starts from the latest price too. Reverse target cost = price × (1 − fee%) × (1 − margin% − profit%). Why: show who loses money at real prices, what happens if nothing changes, and what must be cut when the retailer fixes the price.
- Future cost scan (argus `future_scan`, rules `_shared/futureScan.ts`) runs only on the user's button: web search via Claude, items without a source URL dropped, same-lever changes compounded, then applied to the cost-structure scenario. Why: estimates must be sourced and never run unattended.
