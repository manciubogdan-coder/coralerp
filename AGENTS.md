- Argus (CEO dashboard/AI) runs in the Cloud edge function `argus`: it validates the operational-app session + admin role server-side, reads operational data via the public key and Cloud data via service role; its tables are server-only. Why: AI key and cross-database reads must never live in the browser.
- Shared packaging methods live in the Cloud `packaging_methods` table; reads are public to signed-in app screens, while all writes pass through the admin-validated Argus function. Why: Picking and Sales need one shared source without exposing write access.
- Sales order UI and Excel exports use a shared orderDocument renderer and sanitized original template style metadata; replacement quantities map to existing cuts. Why: preserve customer-specific merged layouts and formatting in both outputs without importing example orders.
- Senior ERP data: reports (builder, assistant) read live from Senior through a queue in private schema `erp_mirror` (`_live_requests`), served by the outbound-only `senior-erp-mirror/` agent via `erp-mirror` edge function (bridge token); only the essential tables listed in `erp_mirror_essential_tables()` are still mirrored, and saved reports store their last result in `_reports`. Why: a full mirror overloaded Cloud; live reads stay current and saved results open instantly.
- Mirror streaming sends sequential batches with adaptive recovery pauses; prereception reads have cancellation and a bounded wait with visible retry errors. Why: shared Cloud operational reads must not compete with uninterrupted mirror writes or spin indefinitely.
- ERP mirror history filtering uses business dates/accounting periods and source foreign-key relationships, never arbitrary audit dates; unknown scopes remain full and are reported, and Cloud finalization preserves existing rows. Why: restricting new transfers must not silently break document relationships or erase retained history.
- ERP accounting period predicates use validated six-digit text comparisons without TRY_CONVERT or TRY_CAST. Why: the source Senior SQL Server rejects those functions; unknown periods must remain safe and retained.
- ERP report SQL builders append scalar expressions to arrays with array_append, not overloaded concatenation. Why: PostgreSQL can parse untyped expression literals as arrays and fail on default counts.
- CEO accounting filters operate on whole accounting periods; commercial browsing uses validated columns, bounded server-side pages and explicit date-column selection. Why: monthly balances cannot support daily precision and raw ERP sources must not imply unverified business roles or totals.
- CEO commercial indicators use an admin-only service-role summary RPC with document types verified from the ERP dictionary, one row per header, and deduplicated partner joins; header amounts remain explicitly distinct from net accounting revenue. Why: table-name guesses, line joins and ambiguous VAT or partner assignments can inflate business figures.
- CEO P&L is computed live from the Senior accounting journal (`C_H_Note_Contabile_Detalii_Conturi`, closing notes NCICV excluded); the mirrored trial balance is only a fallback. Why: Senior's trial balance lags months behind the journal.
- Assistant answers stream NDJSON progress from `erp-mirror/assist.ts` and end with a parameterized SQL template (`{{name}}` placeholders filled server-side by `_shared/templates.ts` with validated literals). Why: visible progress, and saved reports rerun with new dates/partners in one live query instead of a new AI run.
- Argus write actions are proposals stored in Cloud `argus_actions`; they execute only on the user's explicit confirm, server-side with the user's operational session (RLS) and an atomic pending→done claim. Senior stays read-only. Why: AI must never write unreviewed data or duplicate orders.
- Production builds split third-party code into per-package vendor chunks (vite manualChunks). Why: a single entry chunk grew too large for the bundler's parser and broke publishing.
