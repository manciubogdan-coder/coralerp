- Argus (CEO dashboard/AI) runs in the Cloud edge function `argus`: it validates the operational-app session + admin role server-side, reads operational data via the public key and Cloud data via service role; its tables are server-only. Why: AI key and cross-database reads must never live in the browser.
- Argus attachments use a private service-only bucket, with user/thread-scoped opaque references in persisted messages; browser parsers extract Word/Excel/PDF text and scan images, and the admin-validated function resolves those references into model input on every turn. Why: preserve attachment context without public links, oversized transcript rows or trusting arbitrary media URLs.
- Order baxare uses exact product/store Cloud `productie_baxare_magazine`, from live Senior `CT_CantitateBAX.CodArticol = C_D_Note_Contabile.D_ID`. Argus validates override writes; sync preserves overrides. Sheets remain reference-only. Why: never confuse pallets with baxare or borrow across stores.
- Sales order UI and Excel exports use a shared orderDocument renderer and sanitized original template style metadata; replacement quantities map to existing cuts. Why: preserve customer-specific merged layouts and formatting in both outputs without importing example orders.
- Senior ERP data: reports (builder, assistant) read live from Senior through a queue in private schema `erp_mirror` (`_live_requests`), served by the outbound-only `senior-erp-mirror/` agent via `erp-mirror` edge function (bridge token); only the essential tables listed in `erp_mirror_essential_tables()` are still mirrored, and saved reports store their last result in `_reports`. Why: a full mirror overloaded Cloud; live reads stay current and saved results open instantly.
- Mirror streaming sends sequential batches with adaptive recovery pauses; prereception reads have cancellation and a bounded wait with visible retry errors. Why: shared Cloud operational reads must not compete with uninterrupted mirror writes or spin indefinitely.
- ERP mirror history filtering uses business dates/accounting periods and source FK relationships, never audit dates; period predicates use validated six-digit text comparisons (no TRY_CONVERT/TRY_CAST — Senior rejects them); unknown scopes stay full and retained. Why: restricting transfers must not break document relationships or erase history.
- ERP report SQL builders append scalar expressions to arrays with array_append, not overloaded concatenation. Why: PostgreSQL can parse untyped expression literals as arrays and fail on default counts.
- CEO accounting filters operate on whole accounting periods; commercial browsing uses validated columns, bounded server-side pages and explicit date-column selection. Why: monthly balances cannot support daily precision and raw ERP sources must not imply unverified business roles or totals.
- CEO commercial indicators use one admin-validated live Senior SQL query via the existing queue, with verified document types, one row per header and deduplicated partners; failures must not silently use the mirror. Why: current commercial figures must not depend on an incomplete copy or inflated joins; header amounts are not net accounting revenue.
- CEO P&L is computed live from the Senior accounting journal (`C_H_Note_Contabile_Detalii_Conturi`, closing notes NCICV excluded); the mirrored trial balance is only a fallback. Why: Senior's trial balance lags months behind the journal.
- Assistant answers stream NDJSON progress from `erp-mirror/assist.ts` and end with a parameterized SQL template (`{{name}}` placeholders filled server-side by `_shared/templates.ts` with validated literals). Why: visible progress, and saved reports rerun with new dates/partners in one live query instead of a new AI run.
- Argus write actions are proposals stored in Cloud `argus_actions`; they execute only on the user's explicit confirm, server-side with the user's operational session (RLS) and an atomic pending→done claim. Senior stays read-only. Why: AI must never write unreviewed data or duplicate orders.
- Builds use per-package vendor chunks. Why: the oversized entry broke publishing.
- Reception supplier quality-loss eligibility uses the shared receptionQuality predicate for both whole-product and lot-level reports. Why: email variants and quality exports must apply the same inclusive threshold.
- Supplier email quality reports never show the loss percentage; they show only credit kilograms via the shared credit-quantity formatter (whole-product and lot-level), or "Warning!" below the 5% threshold. Why: the supplier must see credit quantities and defects, not our internal loss percentages.
- Scheduled reception emails run through the protected quality-emails Cloud function with server-only routing, review snapshots and atomic delivery claims; SMTP secrets stay server-side and schedules have two daily UTC candidates validated against Bucharest local time. Why: reports must work without an open browser, honor daylight saving, defer unreviewed changes and avoid duplicate deliveries.
- Sales CRM lives inside Vânzări with server-only crm_* tables accessed through sales-crm, which validates approved operational sales/admin sessions; example data stays separate, ERP simulation is labeled, and mailto messages are logged only after user confirmation. Why: operational authentication is external to Cloud, and simulated orders or email drafts must never masquerade as real transactions.

- CRM registry and reports share source-filtered analytics; order values are line-level, kilograms are explicit, frequency is shared with the server, and unknown quantities stay nullable. Why: simulations, caseroles and repeated document totals must not inflate commercial indicators.
- CRM additional contacts use a validated JSON array on the customer; note sentiment runs through an operational-authenticated server-only AI action and failures do not discard notes. Why: retain existing customer compatibility and protect model credentials.
- CRM Senior sync runs one month per request (client loops newest→oldest), reads only customer orders (CC) in 500-row pages (the live Senior reader's cap) and creates customers only when they have orders. Why: a single all-at-once sync exceeded the function time limit and flooded the registry with inactive partners.
- Senior product inheritance uses the shared productRecipes matcher with explicit retailer suffixes, compatible recipe composition and paginated reads across operational recipes and Cloud groups; existing recipes/groups are never overwritten. Why: new weights need proportional ingredients without merging unrelated products or erasing manual setup.
- Recipe editing preserves existing ingredient row IDs and checks each write; the product editor locks the full save until recipes and distribution finish loading. Why: destructive replacement and early/double submits can lose ingredients or duplicate recipes.
- Discarded finished-goods resets use a shared preview/apply service with paginated reads, checked compare-and-set writes, pool clearing before date-scoped allocation resets and session-derived status; never call allocation-return helpers. Why: discarded goods must not reappear, real production must survive, partial/concurrent changes must be visible.
- Origin reservations protect firm production: Picking uses its own goods; other orders use free surplus with confirmation. Why: today's goods must not cover tomorrow.
- Production and Picking share same-day advance projections; manual unproduced plans require later firms. Picking uses max(production, own pool), not their sum, and filters sessions by selected Bucharest day. Never persist projections. Why: protect goods and avoid duplicate counts.
- Purchase forecasts share date-keyed supplier schedules and stock projections with paginated reads. Why: deliveries must retain each ETA in both screen and Excel.
- Leaf warnings share receipt-based Bucharest day rules and original positive-stock lots. Why: grouping must not hide old lots or age fresh stock.
- AuthContext times out legacy auth/profile calls after 20s with a Romanian error. Why: avoid endless login.
